# Mobile money transactions: a linear algebra analysis

Matrix and vector methods applied to 1,720,181 synthetic mobile money
transactions, in NumPy and pandas. No machine learning library is used: the
point is to show the algebra, so every step is written out and then checked
against an independent computation.

## The data

The [Synthetic Mobile Money Transaction Dataset](https://data.mendeley.com/datasets/zhj366m53p/2)
(DOI `10.17632/zhj366m53p.2`), generated by the MoMTSim multi-agent platform and
described in a *Data in Brief* article by Azamuke, Katarahweire and Bainomugisha.
Published under CC BY 4.0.

1,720,181 records, ten columns, 144 consecutive hourly steps.

**The file is not in this repository** — it is 149 MB and has a stable DOI.
Download `synthetic_mobile_money_transaction_dataset.csv` and put it in `data/`:

```
data/synthetic_mobile_money_transaction_dataset.csv
```

Because the records are simulated, every pattern here is a property of the
simulation and of the behaviour it was calibrated to reproduce. The methods
transfer; the numbers would not.

## Running it

```bash
python -m venv .venv
.venv/Scripts/activate        # Windows;  source .venv/bin/activate  on macOS/Linux
pip install -r requirements.txt
jupyter lab
```

Run any notebook top to bottom — each loads and cleans the data itself, so they
work in any order. A full pass is about 20 seconds each; the four together take
under 90 seconds.

## Layout

```
notebooks/
  csc1105.py          loading, cleaning, sampling, standardising — shared by all four
  01_audit.ipynb      audit, cleaning decisions, transaction type summary
  02_vectors.ipynb    transactions as vectors; norms, dot products, angles
  03_monitoring.ipynb count matrix over time; a balance-change operator
  04_forecast.ipynb   least squares via the normal equations, tested against a baseline
figures/              plots written by the notebooks
```

All cleaning lives in `csc1105.py` rather than in the notebooks, so that every
notebook analyses the same table and the counts cannot drift between them.

## What it finds

**Fraud is structural, not statistical.** All 175,518 fraudulent records are
`TRANSFER`; the rate in every other transaction type is exactly zero. Within
transfers it is 0.308. This is a property of how the simulator generates fraud.

**Scaling decides what a distance means.** Between two sample transactions, the
two initiator balance columns supply 98.41% of the squared distance and the
amount only 0.42% — an unstandardised distance is almost entirely a statement
about account balances. After standardising, the amount becomes the largest
contributor at 40.55%. Same two transactions, a different question answered.

**Similarity carries no signal about the label.** Across 3,996 random pairs,
pairs with differing fraud labels came out very slightly *more* similar
(mean cosine +0.058) than pairs sharing a label (+0.035). Geometry alone does
not identify fraud.

**The balance identity detects settlement, not fraud.** Of 688 sampled
transfers, 20.49% fail `new − old = ±amount` at a tolerance of 0.01. The driver
is insufficient funds (75.61% of underfunded transfers fail, against 17.00% of
funded ones), not the fraud label — controlling for funding reverses the
apparent association.

**Volume and risk are different problems.** The busiest hour carries 30,489
transactions, 2.55× the average, at a below-average 4.08% fraud rate. The
riskiest carries a fifth of that volume at 18.37%. Busy is a capacity problem;
risky is a control problem.

**The trained model does not beat persistence.** A least squares fit of next-hour
count on current-hour count, solved through the normal equations
(intercept 1132.42, slope 0.9101), is 11.9% *worse* than "assume next hour
equals this hour" on MAE, and 2.9% better on RMSE. Consecutive hours already
correlate at 0.9064, so the previous count is most of the information. Reported
as found: the baseline is the result.
